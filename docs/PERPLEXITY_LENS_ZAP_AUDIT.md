## PART 2 — Corrected NYC ZAP Spatial Implementation

You're right to flag the identifier conflict — `r67x-e97r` in my earlier response was an error; the only verified official identifiers are `hgx4-8ukb` (ZAP Project Data) and `2iga-a6mk` (ZAP BBL). Correcting that now.

### ZAP BBL field verification (confirmed directly from the dataset page)

`ZAP BBL` (`2iga-a6mk`) contains 132,000 rows, one row per tax lot associated with a ZAP project, with these columns: `project_id` (Text), `bbl` (**Number**, not text), `validated_borough`, `validated_block`, `validated_lot`, `validated` (flag), `validated_date`, `unverified_borough`, `unverified_block`, `unverified_lot`. BBL format: borough code (1 digit) + tax block (1–5 digits, zero-padded to 5) + tax lot (1–4 digits, zero-padded to 4), validated via Geosupport — the city's official geocoding engine.

**Leading-zero requirement:** yes — block and lot are stored zero-padded within the concatenated numeric BBL, but because the field type is Number, leading zeros are implicit in the 10-digit value, not a separate text-formatting concern. When joining, cast both sides to the same 10-digit zero-padded numeric or string representation — do not join a raw unpadded integer against a padded string.

### Why permit-only joining is insufficient (confirmed, matches your instruction)

ZAP BBL contains records for every tax lot tied to a land-use application — including projects that never produce a building permit within your ingestion window, or that are still active/pending. Joining ZAP only to existing permits would systematically drop every entitlement-stage parcel that hasn't reached permitting yet — which is precisely the earlier-signal value ZAP exists to provide.

### Official parcel-location source: PLUTO / MapPLUTO

Confirmed directly from the DCP PLUTO Data Dictionary (22v2 and later editions):

| Field | Format | Detail |
|---|---|---|
| `BBL` | Numeric, 10 digits | Same concatenation logic as ZAP: borough (1 digit) + block (1–5 digits, zero-padded) + lot (1–4 digits, zero-padded)  [nyc](https://www.nyc.gov/assets/planning/download/pdf/data-maps/open-data/PLUTODD.pdf?r=22v2) |

[data.cityofnewyork](https://data.cityofnewyork.us/City-Government/Primary-Land-Use-Tax-Lot-Output-PLUTO-/64uk-42ks)

**Update frequency:** PLUTO/MapPLUTO is released in periodic versioned editions (e.g., 22v1, 22v2, 24v3, 25v4) rather than a continuous rolling update — treat it as a periodic snapshot, refreshed roughly semi-annually to annually based on the version history found. [nyc](https://www.nyc.gov/assets/planning/download/pdf/data-maps/open-data/PLUTODD.pdf?r=22v2)

### Duplicate and multi-lot handling

**Confirmed limitation:** for condominiums, PLUTO's BBL refers to the billing lot, not each individual unit — so a ZAP application tied to a condo building may resolve to a single shared BBL representing multiple legal units.  Multiple buildings can also reside on a single tax lot, and a separate DCP building-centroid dataset explicitly documents that "multiple rows may contain the same base_bbl value" for this reason.  For your purposes: **join at the parcel/BBL level, not the building level** — this means a single ZAP project touching a condo or multi-building lot maps to one parcel centroid, and you must deduplicate on BBL before counting projects, not before counting parcels. [nyc](https://www.nyc.gov/assets/planning/download/pdf/data-maps/open-data/meta_mappluto.pdf)

### Invalid/unverified BBL handling

ZAP BBL itself distinguishes `validated_*` fields (Geosupport-confirmed) from `unverified_*` fields (manually entered, populated only when `validated_borough` is blank, meaning no Geosupport match was found).  **Product rule:** only join records where `validated = true` (or equivalently, `validated_borough` is non-blank) to PLUTO for spatial placement. Records with only `unverified_*` fields populated should be counted in your entitlement panel's totals but excluded from the map/H3 layer, and flagged in the UI as "location not independently verified." [data.cityofnewyork](https://data.cityofnewyork.us/City-Government/Zoning-Application-Portal-ZAP-Project-Data/hgx4-8ukb)

### Should H3 be assigned from parcel centroid or another geometry operation?

**Use the PLUTO `Latitude`/`Longitude` centroid fields directly.** Do not attempt polygon-based H3 cell-coverage operations (e.g., assigning a cell to every H3 cell a parcel's actual boundary intersects) — that requires the full MapPLUTO geometry file (shapefile/FileGDB), not the flat PLUTO table, and is disproportionate engineering effort for a two-day prototype.

**Resulting limitation to disclose explicitly:** centroid-based H3 assignment means a large parcel that spans multiple H3 cells will be assigned to only one cell — its geometric centroid — which can misplace large-site entitlement activity relative to smaller, more precisely geocoded permit records in the same area. This is a real precision mismatch between your ZAP/PLUTO layer (parcel-centroid, coarser for large lots) and your NYC permit layer (also address/BBL-derived, similarly parcel-level) — so the resolution difference here is smaller than the SBA-vs-permit mismatch, but not zero, and should be labeled with the same `GeoResolution` discipline you're already using: `"PARCEL_CENTROID"` as a fourth explicit value.

### Window, status handling, and de-duplication rules

**Which ZAP date defines entry into the 24-month window:** ZAP Project Data tracks the lifecycle from "Noticed" (will appear before the City Planning Commission in 30+ days) or "Filed" (formal CEQR/land-use submission) through completion.  Use the earliest of these two milestone dates — Noticed or Filed — as the window-entry date, since either represents the first point the application became a real public commitment, not merely a pre-application inquiry.

**Which statuses are included:** include all statuses (Noticed, Filed, and every completion state) in the underlying panel data, but display status as an explicit, filterable field — never silently exclude withdrawn or disapproved records, since their presence itself is informative (e.g., "this parcel had a proposal that was withdrawn" is a legitimate research fact).

**How withdrawn, terminated, disapproved, completed, and active projects appear:** show a status badge per project — `Active/In Review`, `Approved`, `Disapproved`, `Withdrawn`, `Terminated` — and let the count panel be split by status rather than collapsed into one number, so "12 entitlement applications, 8 active, 3 withdrawn, 1 disapproved" is visible at a glance.

**How multi-BBL projects avoid duplicate counting:** since ZAP BBL is one row per tax-lot-per-project (confirmed: "each row is a tax lot associated to a project"), a single project spanning multiple lots will have multiple BBL rows. **De-duplicate on `project_id` when counting projects**; only use the BBL-level granularity for spatial placement (a multi-lot project may legitimately appear in more than one H3 cell, which is correct — it physically spans that area), but your project *count* metric must be `COUNT(DISTINCT project_id)`, never `COUNT(rows)`.

### Why ZAP must remain separate from the permit ranking

Entitlement and permit data represent genuinely different lifecycle stages, confirmed by the GlobeSt entitlement-gap research from the earlier analysis — permits are a lagging confirmation signal, while entitlement/ULURP applications represent an earlier, distinct commitment stage that may never reach permitting, may take years to convert, or may be withdrawn entirely.  Blending the two into one composite signal would conflate "committed construction is happening now" with "a land-use proposal exists that may or may not proceed" — two claims with very different evidentiary weight. Keeping them as separate, clearly labeled panels (not merged into your existing lens ranking) preserves the auditability discipline the rest of your product already commits to.
